# Spec: AI-generated case report PDF

Intent: [intent.md](intent.md) · Status: accepted (owner, via /tdd implement, 2026-11-15) · Last updated: 2026-11-15
Depends on: [ai-deep-agent-research](../ai-deep-agent-research/spec.md) (Deep Agent, `subagent` thinking events). Uses: [annotation-color-system](../annotation-color-system/spec.md) colours when present.

## Summary
When the user asks for a case report in chat, the main Deep Agent spawns a `case_report` subagent. The subagent reads the workspace and the current conversation, then writes a structured report plan. The browser captures the 3D views and slice images that plan asks for, and the server builds a University of South Florida–titled PDF in the layout of the reference VSP case report. The PDF is attached to the current chat session and can be opened or downloaded from the chat. The thinking trace shows each stage.

## Requirements

### Agent and plan
- R1. A subagent named `case_report` is registered with the main agent. The main agent delegates to it when the user asks for a case report, report, summary PDF or similar.
- R2. Its tools are read-only: the existing workspace read tools and geometry measurement tools, `list_case_annotations` (added: the manifest carries no annotations, so callout ids need a read-only listing), `read_session_transcript`, and `submit_report_plan`. It cannot call the research subagent, stage proposals, or write application data (assistant spec R61).
- R3. `read_session_transcript` returns the current conversation's human and assistant turns as plain text (latest 24, each capped at 4000 characters), plus any research citations from that conversation. It never returns other conversations.
- R4. `submit_report_plan` validates and stores a report plan, then returns a `report_id`. The plan holds: title; a summary (≤ 1200 chars); a findings list; a measurements table (name, value, unit, source tool); a sources list; and an ordered `shots` list. The plan is rejected (with a reason the agent can fix) if it references an unknown object or annotation id, or has more than 16 shots.
- R5. Each shot is one of:
  - `view`: preset `anterior` | `posterior` | `left` | `right` | `superior` | `inferior` | `hero_oblique`, plus the object ids to show.
  - `annotated_view`: a preset plus the annotation ids to feature, each with a callout label of 40 chars or fewer.
  - `slices`: axial, sagittal and coronal images through a centre point. The centre is a given annotation, the defect (implant/candidate object centre), or the volume centre.
- R6. The result envelope gains an optional `report_job` field `{report_id, conversation_id, status: "needs-captures", shots}` when a plan was submitted this turn. Clients that ignore it are unaffected.

### Capture (browser)
- R7. On `report_job`, the app renders each shot offscreen at a fixed size (1200×900 for views, 600×600 per slice) as PNG. It uses the same scene, meshes, materials, visible annotations and annotation colours as the viewport.
- R8. Capture does not change what the user sees or what is saved. Camera, selection, visibility, slice positions, the dirty flag and the persisted project are identical before and after. No annotation is created or edited.
- R9. `annotated_view` shots draw each featured annotation's callout label, using the annotation's palette colour as a leader line and swatch. Non-featured annotations stay visible but are not labelled.
- R10. Captures upload to `POST /api/ai/reports/{report_id}/captures`. The server accepts only PNGs whose ids match the plan, 2 MB or less each and 24 MB or less per report. Anything else is rejected without building a PDF.

### PDF
- R11. The server builds a US Letter PDF:
  - **Cover page:** header "University of South Florida" and "Cranial Reconstruction Case Report"; a case information table (project, case, object, revision id, generated date/time, "Generated by: AI assistant (demo)"); up to three hero images; the summary.
  - **Anatomy pages:** "Preoperative Anatomy" (5-view grid: left, right, anterior, superior, posterior). If a candidate or implant object exists, "Defect and Proposed Repair" with the same grid.
  - **Annotated pages:** one per `annotated_view`, plus a three-slice panel page for each `slices` shot.
  - **Findings page:** "Findings and Conversation", with findings, the measurements table, a conversation summary and the sources list with links.
- R12. Every page has the footer "University of South Florida · Case <case name> · Page n of N · Demonstration only, not for clinical use". No logo, and no Stryker, 3D Systems or VSP name, logo, agreement or terms text appears anywhere.
- R13. The PDF is stored in memory against the conversation: up to 5 reports per conversation, oldest dropped first, 30 MB max each. It is available at `GET /api/ai/reports/{report_id}.pdf` and listed at `GET /api/ai/conversations/{conversation_id}/reports`. It is lost on server restart, like conversation memory.
- R14. A report id from another conversation or an unknown id returns 404. Reports are never written to the application database or the project package.

### Chat and thinking UI
- R15. The thinking trace shows the report run as a subagent group (`subagent: "case_report"`):
  - Server-side steps: spawned, reading the workspace, reading the conversation, drafting sections, returned.
  - Client-side steps added to the same group: "Capturing views (k/N)", "Building PDF", "Report ready".
  - A failure shows a `failed` line with a plain reason.
- R16. When ready, the assistant message shows a report card with the title, page count, "Open PDF" (new tab) and "Download".
- R17. A failed capture or build leaves no PDF. The card shows the error and a "Try again" action, which re-runs capture and build for the same plan without another model call.

### Tests
- R18. Plan validation, the capture upload limits, PDF structure (page count, cover text, footer on every page, absence of the forbidden names), the session storage limits and the frontend capture invariants (R8) are covered by offline tests.

## Success criteria
- S1. Given a scripted main agent that delegates to `case_report`, and a subagent that submits a valid plan with 9 shots, when the turn streams, then the client receives `subagent` lines for `case_report` (spawned → steps → returned) and a result envelope whose `report_job` lists those 9 shots.
- S2. Given a plan that references an annotation id not in the revision, when `submit_report_plan` is called, then it returns a validation error naming the id, and no report is stored.
- S3. Given a submitted plan and 9 valid PNG captures, when they are posted, then `GET …/reports/{id}.pdf` returns a PDF whose page 1 text includes "University of South Florida" and the case name, and every page's footer contains "Page n of N" and "not for clinical use".
- S4. Given any generated PDF, when its text is extracted, then it contains none of "Stryker", "3D Systems" or "VSP".
- S5. Given a capture upload with a non-PNG file, an unknown shot id, or a file over 2 MB, when posted, then the server responds 4xx and no PDF exists for that report.
- S6. Given conversation A's report id, when requested with conversation B's listing or an unknown id, then it is not listed, and the direct URL for an unknown id returns 404.
- S7. Given the app with a chosen camera, a selection and some hidden objects, when a 9-shot capture runs, then the camera, selection, visibility, slice positions and dirty flag are unchanged afterwards and no annotation was added.
- S8. Given a sixth report in one conversation, when it is stored, then the oldest is dropped and the listing shows 5.
- S9. Given a ready report, when the chat renders, then a card shows "Open PDF" and "Download", and a forced build failure shows the error and "Try again".

## Design
**Two-phase flow.** The agent cannot pull images from the browser mid-turn, so the turn ends with a plan, and the browser finishes the job. This is the order:
1. The `case_report` subagent submits a plan into a `ReportStore`. The store is in memory, keyed by conversation id, and has the same lifetime model as `ProposalStore`.
2. The result envelope carries `report_job`.
3. `AiChatPanel` hands the job to a capture service. The service drives an offscreen render path in the viewport: a separate camera and render target, so the visible canvas never moves. Slice images come from the same slice-sampling code the dock uses.
4. The service uploads the PNGs.
5. The server renders the PDF with `reportlab` and marks the report ready.

The subagent's events come from the same translator as research (`subagent` kind). Client-side capture/build progress is appended to the same group by the panel.

**Shot centre for slices.** A named annotation centres on its anchor (ROI centre, curve centroid, otherwise first point). For "defect", the browser uses the first visible ROI, closed curve, highlight or plane annotation on the active revision; otherwise the volume centre. The plan records which kind was requested. (Changed during build: the browser has no implant-region geometry to take a bounding box from — see Flagged concerns.)

**Default shots.** When the subagent leaves `shots` empty, `submit_report_plan` fills the reference layout: 3 hero views, the 5-view anatomy grid, the 5-view repair grid when a candidate exists, one annotated view when there are callouts, and one three-slice panel.

## Decisions
- D1. Build the PDF on the server with `reportlab` (pure Python, no system libraries). Why: deterministic, testable offline, and keeps layout code next to the plan schema. Alternatives: browser jsPDF (layout code in the UI, harder to test text), WeasyPrint (needs system libraries).
- D2. Two-phase plan → browser capture → server build. Why: only the browser can render the WebGL scene. Alternatives: server-side headless rendering (heavy, duplicates the renderer), screenshotting the live canvas (moves the user's view).
- D3. Offscreen camera/render target for capture. Why: R8 requires the user's view to stay untouched. Alternatives: move the real camera and restore (flicker, race with user input).
- D4. Highlights in the report are the user's own annotations in their colours, plus callout labels drawn at capture time. Why: AI writes are disabled (R61), and the owner wants their annotation tools to carry the highlights. Alternatives: AI-created annotations through the proposal flow (slow for a demo, needs accepts).
- D6. "Defect" slice centre = first visible ROI / closed curve / highlight / plane annotation, else volume centre. Why: the browser has no implant-region geometry; owner approved for the demo. Alternatives: backend-computed defect centre (later).
- D7. Captures render the single active document as displayed. Why: the 3D view holds one document at a time; owner approved for the demo. Alternatives: load extra documents into an offscreen scene (later).
- D5. Store reports in memory per conversation. Why: the owner chose "saved on the current chat session for now". Alternatives: persist on the case (a later feature).

## Flagged concerns
- Resolved (owner, 2026-11-15): keep the "defect" slice centre as the first visible ROI / closed curve / highlight / plane annotation, else the volume centre (see D6).
- Resolved (owner, 2026-11-15): captures render the active document with its visible annotations; per-shot `objects` lists are recorded but do not toggle objects (see D7).
- Open: browser capture (WebGL offscreen render) is unit-tested only through its pure parts; it has not been checked in a running browser in this build.
- The reference report's structure is copied, but none of its branding or legal text is (R12, S4). The "University of South Florida" title is used as plain text with no logo, per the owner. It is the team's own institution, but check USF's name-use rules before any public posting.
- Captures are the heaviest step: about 9–16 offscreen WebGL renders. On a slow laptop this may take several seconds. Progress is shown (R15).
- The report summarises AI chat content, which may contain model errors. Every page says it is a demonstration only.

## Out of scope
- Logo, signatures, surgeon agreement, terms and conditions, ordering and manufacturing.
- Cutting and positioning guide design pages.
- Editing a generated PDF; persistence beyond the server process (persisting reports on the case is deferred).
- Research inside the report run (the report cites sources already found in the conversation).
